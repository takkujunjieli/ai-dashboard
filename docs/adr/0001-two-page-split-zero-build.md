# 0001. 信息页/交易页两页分离,交易页保持零构建

日期: 2026-07-10
状态: 已接受

## 背景

系统从消息聚合演进为短线研究台后,单页五 tab 里"阅读型内容"(新闻/社区)和
"交互型数据"(K线/期权/GEX)挤在一起:手写 SVG 图表没有缩放/十字线,嵌入式卡片
做不了价格轴对齐的行权价梯,阅读动线也被数据区块打断。

## 决策

1. **按消费模式分两页**:`index.html` 信息页(阅读),`trading.html` 交易页(交互工作台)。
   边界按内容的消费模式划分,而非数据来源——财报日历/EPS/评级虽是 API 数据,
   但属阅读型,留在信息页。
2. **交易页仍为零构建静态页**:不引入 React/Vite,图表库用 TradingView
   lightweight-charts 经 CDN 引入,ES modules 组织代码。
3. **交易页布局为单票工作台**:research 组切票,K线主图 + 共享价格轴的行权价梯
   + 共享时间轴的盘中净GEX副图 + 详细期权面板。
4. **数据刷新 PAT 分级**:有 PAT(与采集控制共用)则 60s 认证轮询 GitHub contents
   API,无 PAT 手动刷新——匿名限流 60 次/小时无法支撑自动轮询。

## 备选方案

- **Vite + React SPA**:组件化更正规,但 Actions 需加构建步骤、依赖需长期维护,
  而交互瓶颈在图表库而非框架,收益不成比例。
- **独立仓库部署**:解耦最彻底,但数据在原仓库,跨仓库读取+双仓库维护成本高。
- **单页内改造**:不新增页面,但阅读/交互混排的根本问题无解。

## 后果

- 部署链路不变(Actions 写 JSON → Pages 托管),无构建产物。
- 两页共享 data/*.json 与部分工具函数,需拆出共享 JS 模块避免复制。
- 若未来交互复杂到 lightweight-charts + vanilla 撑不住,迁移 SPA 时本 ADR 需复审。
- 信息页移除 个股/期权 tab,旧锚点(#stock/#options)重定向到交易页。
